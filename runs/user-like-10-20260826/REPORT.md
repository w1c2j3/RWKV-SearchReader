## 本轮定位到的根因

1. `4090` 是最大输出预算，不应在大输入时仍固定申请满额。20 份摘要会让 input + requested output 超过模型 16384 context。
2. 13.3B final 在长列表任务上会形成稳定重复周期；增大输出上限只会让重复更长。
3. 当前多轮 contextualize 能找回对象，但没有稳定保留“当前为 3.1”这样的比较锚点，所以“下一个版本”仍可能选到历史版本。
4. 审核补检会把 10 份材料扩到 15 至 20 份，并显著增加摘要调用量；错误审核也会造成无新查询的补检请求。
5. 单网页摘要虽然都实际执行了，但有 29/139 因数字校验失败降级，降级材料通常更长，也会进一步挤压 final context。

## 已完成的通用修复

- final 发生 context rejection 时，保留摘要输入，按 `4090 → 2045 → 1022 → 511` 自动缩小本次输出预算重试；短问题仍以 4090 为最大值。
- 对最终回答做机械式重复周期去重，包括重复 Markdown 条目和单行顿号列表，不改写模型的正常表述。
- 删除空来源栏；代码块内不再插入 `[S#]`。
- final 的简短要求增加“只回答所问内容”和“不推断材料没有的信息”。

修复后 U06 正常返回并正确回答：最近一次是 2026-08-21 19:30（UTC+8）发布的「雪淞幽梦」版本前瞻。U10 也从 502 恢复，并正确继承《绝区零》这一对象；但仍把历史 2.7 误判为 3.1 的下一版本，因此语义质量仍判失败。

## 下一步重点

下一轮不应继续堆提示词，而应解决证据链的时间关系：让 contextualize 保留上一轮的版本/日期锚点，让字段证据选择明确区分“当前版本、历史版本、已宣布的下一版本”，再把选中的证据顺序置于 final 问题之前。否则工程链路虽然能返回，模型仍可能从 20 份材料中选错时间方向。

## 漏斗架构修正

用户复核后确认，正确主链不是把全部逐网页摘要直接塞给 final，而是按上下文 chunk 做并发漏斗归并。当前实现已改为：每个 chunk 最多 4 个输入节点且不超过 6000 个渲染字符；典型 20 份材料先并发归并为约 5 份，如果末层仍超过 9000 字符 final 材料预算，就继续下一层。每个归并节点使用 `([source_ids], summary)` 二元组保留完整来源谱系。

用 U06 的真实 20 份逐网页摘要重放验证：模型调用严格为 5 个并发 `reduce` 加 1 个 `finalize`；5 个 reduce 输入为 1007–3073 字符，final 输入由原来的约 1.5–1.7 万字符降为 1896 字符，仍完整请求 4090 最大输出，并正确回答「雪淞幽梦」前瞻。

U10 的真实材料需要两层漏斗（20 → 5 → 3 → final），final 输入 5223 字符，同样不再发生 16K context 错误；但答案仍错误选择了历史版本，说明漏斗解决的是上下文与材料利用率，不会自动解决时间证据选择错误。

部署后又通过正式 `/v1/answer` API 完整重跑 U06（request `2b0f323c32214bcfb44ff9948b332588`）：Tavily 与 20 个逐网页摘要正常执行，trace 显示 1 层 `20 → 5`，5 个 reduce 输入为 1638–3613 字符，final 输入 5928 字符并保留 `max_tokens=4090`，没有 context retry，最终回答正确。
